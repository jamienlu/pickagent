## 主动回忆题

1. 为什么 model adapter 不应执行工具循环？循环次数、成本预算、停止条件、工具权限和失败处理属于应用策略。 adapter 自己循环：

   1. Runtime 无法审计实际调用次数。

   2. 更换供应商可能改变业务行为。

   3. adapter 容易混入重试、工具执行和预算判断。

   4. 离线测试无法准确控制每一步。

   5. 因此 adapter 每次只完成一次“上下文 → AgentDecision”转换，循环由 Runtime 管理。

2. maxSteps=3 最多执行几次工具？最多 2 次。 N 个步骤最多执行 N−1 次工具。

3. callId 不一致时在哪一层拒绝？应由核心契约层拒绝。

   1. ToolRegistry 从原始 ToolCall 复制 callId，handler 无权改写。

   2. AgentContext.Exchange 检查调用与结果的 callId。

   3. AgentStep 检查 observation 是否属于当前调用。

   4. model adapter 负责保留供应商返回的原始 ID，但关联一致性不能只依赖供应商 adapter。

4. `ToolExecutionException` 与未知 `RuntimeException` 应分别怎样处理

   1. ToolExecutionException：表示 adapter 已识别的预期工具执行失败。

   2. Runtime 转换为 typed ToolFailed，保留原 ToolCall、错误信息和 cause，然后停止，不自动重试。

   3. 未知 RuntimeException：通常代表程序错误、契约违例或映射 bug，应原样向上抛出，由统一异常监控处理，不能伪装成工具失败或网络故障。

5. 供应商差异何时升级为核心 capability？

   1. 留在 adapter：

       差异能在 adapter 内无损归一化,例如sdk类型等，可映射进现有核心语义且不会丢失应用关心的信息。

   2. 升级为核心 capability：

      应用必须根据该能力做业务决策。

多个用例都需要声明或检查该能力。

无法映射进现有模型而不丢失关键语义。

它会改变 Runtime 的编排或安全策略。


## time1

##### Strict mode 的三个必要约束

1. 函数工具显式设置 `strict: true`。2. 参数 schema 中每个 object 都设置 `additionalProperties: false`。3. `properties` 中的所有字段都进入 `required`；不引入可选字段、数组或嵌套对象。


##### “失败都是内置事件”不成立。

1.`refusal`、`incomplete` 或响应失败可能是供应商协议暴露的状态/内容类型；

2.missing、extra、blank 是本地 schema/运行时校验结果；

3.未授权是业务策略结果；

4.工具异常、传输故障和程序错误也有各自的 typed result 或异常边界。不能把这些来源不同、可恢复性不同的失败压成一个所谓的 SDK 内置事件。


##### OpenAI mapper 的依赖方向

com.pickagent.w2.core.ToolDefinition                 ↑ readscom.pickagent.w2.openai.OpenAiFunctionToolMapper → openai-java SDK反向依赖会让核心端口出现 `FunctionTool`/SDK 类型，使替换供应商时必须修改核心与应用服务，从而破坏供应商中立性。

## time4

模型生成合法参数”为什么仍不代表“模型获得了执行权限


安全结论：模型生成合法参数，只证明数据形状合规；执行权限必须由可信应用根据真实身份、资源范围和业务策略授予，模型不能通过合法参数给自己提权。
