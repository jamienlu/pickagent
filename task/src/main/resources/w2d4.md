## 主动回忆题：

1. mapper、`ToolRegistry` 和业务授权层分别拒绝什么错误？

   1. mapper无调用、多个调用、畸形 JSON、非对象根节点、非字符串参数、空白 `call_id/name`

   2. 未注册工具、缺少参数、额外参数、空白参数值

   3. 未登录、角色无权限、跨租户/资源越权、缺少人工审批、超过业务额度

2. 为什么不能只取第一个 `function_call`？

  静默丢失其他调用；

无法判断调用之间是否有依赖；

导致部分副作用已经执行、其他调用却未处理；

·下一轮模型收不到完整的调用结果；

使审计记录与供应商响应不一致。

3. `call_id` 解决了什么问题，又没有解决什么问题？

   1. 模型知道某个工具结果属于哪次调用

   2. 参数是否合法；工具是否存在；用户是否有执行权限；是否已经执行过；幂等或 exactly-once；多调用的顺序和依赖；reasoning 状态保存；工具结果是否真实可信。

4. reasoning items 丢失会怎样影响下一轮模型调用？

`call_id` 只能关联工具结果；reasoning items 保存模型继续当前推理所需的供应商侧上下文；缺少之前的假设、计划和推理状态；无法理解为什么发起这次工具调用；重复推理或重复调用工具；得到不一致或不完整的最终答案；在要求续接 reasoning item 的协议路径上失败


## **故障分类与处置**

分类不能只看 HTTP 状态。adapter 先读取 HTTP 状态、结构化 `error.type` / `error.code` 和传输异常，再映射为 provider-neutral`FailureKind`；`RetryPolicy` 不依赖 OpenAI SDK 类型或错误文案。

> [Error codes][https://developers.openai.com/api/docs/guides/error-codes)](https://developers.openai.com/api/docs/guides/error-codes)、[Rate)
> [[Rate](https://developers.openai.com/api/docs/guides/error-codes)、[Rate) limits]([https://developers.openai.com/api/docs/guides/rate-limits](https://developers.openai.com/api/docs/guides/rate-limits)
1. 临时限流 

   1. HTTP `429`；已明确的突发流量场景为 `error.type=rate_limit_error`、`error.code=slow_down`。必须先排除下面的额度/账单

   2. 重试，受次数和总等待预算限制

   3. `Retry-After` 存在时至少等待该时长；缺失或无效时指数退避加 jitter。失败请求本身也消耗每分钟限额，不能紧密循环

2. 服务过载

   1. http `503` ;+ `error.type=service_unavailable_error` + `error.code=server_is_overloaded`

   2. 重试，受预算限制

   3. 模型容量暂时不足；遵守 `Retry-After`，缺失时增加等待

3. 超时

   1. transport/SDK 的明确 timeout 类别

   2. 重试，受预算和幂等保护限制

   3. 网络拥塞、服务负载或复杂请求可能是暂时的；但“不知道服务端是否已成功”意味着副作用请求必须先具备幂等性

4. 账单/额度

   1. HTTP `429`，并优先检查 `error.code`、`credit_balance_exhausted`、`organization_spend_limit_exceeded`、`project_spend_limit_exceeded`、`organization_usage_limit_exceeded`；不能只看较宽泛的 `error.type=insufficient_quota`

   2. 不重试

   3. 增加重试不会补充信用余额，也不会改变 spend/usage limit；需要用户或管理员处理

5. 认证

   1. HTTP `401`（adapter 可进一步保留认证错误类别）

   2. 不重试

   3. 原样重发不会修复错误、过期或撤销的凭据，也不会获得组织/IP 权限

6. 非法请求

   1. HTTP `400` + `error.type=invalid_request_error`，并读取 `error.param` / `error.code` 定位字段

   2. 不重试

   3. 必须先修正参数、格式、大小或业务输入；原样重试只会重复失败

## time2

### **相同 HTTP 状态、不同处置**

`429 + error.code=slow_down` 是临时流量上升过快，可以在预算内退避重试；

`429 + error.code=credit_balance_exhausted` 是预付额度耗尽，必须充值而不是重试。

因此 `429` 不能直接等价为“可重试”。官方还明确说明：`Retry-After` 可能出现在临时限流响应上，但它不代表额度、账单等需要人工处置的错误可由重试解决。


### RetryPolicy 约定

 attemptsMade 表示已经发出的请求总数，并包含刚刚失败的这一次。attemptsMade=1时，决策器是在决定是否安排第一次重试；maxAttempts=3 最多发出初始请求加两次重试。


-公式：exp = min(maxBackoff, baseDelay × 2^(attemptsMade-1))；calculated = min(maxBackoff, exp + jitter(exp))；若有合法 Retry-After，最终 delay = max(calculated, Retry-After)。


如果已达到 maxAttempts 或总等待预算，立即停止；如果“已等待时长 + 下一次 delay”将超过总等待预算，也停止。


RetryPolicy 只返回 RetryAfter(delay) 或 Stop(reason)，不调用 Thread.sleep。真实 sleep 会让单元测试变慢、受调度器影响且产生偶发失败；注入 jitter 后可以直接断言纯计算结果。生产层可使用调度器或虚拟线程消费该决策。


### time3

1. call_id 与 operationKey 分别由谁生成？

 `call_id` 由模型供应商为工具调用生成；`operationKey` 由应用为业务操作生成。

2. 重试安全由 RetryPolicy 还是幂等执行器保证？

`RetryPolicy` 只保证“哪些故障、何时、最多重试多久”；副作用重试安全由幂等执行器以及生产级持久化/事务边界保证

3. 哪些工具天然只读，哪些必须有业务幂等保护？

查询订单状态、搜索文档、读取天气等无写入语义的工具通常天然只读；扣款、退款、发消息、创建订单、发券、修改权限等工具必须使用业务 `operationKey`、授权与持久化幂等保护。只读也不等于完全无副作用：计费、审计日志或下游计数仍需单独评估
