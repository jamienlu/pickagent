## 主动回忆题

1. `attemptsMade=1` 和 `maxAttempts=3` 分别表示什么？

attemptsMade 表示已经发出的请求总数，并包含刚刚失败的这一次`attemptsMade=1`决策器是在决定是否安排第一次重试，maxAttempts=3 最多发出初始请求加两次重试。

2. 两个 HTTP 429 为什么可能需要完全不同的处置？

   1. `429 + error.code=slow_down` 是临时流量上升过快，可以在预算内退避重

   2. `429 + error.code=credit_balance_exhausted` 是预付额度耗尽，必须充值而不是重试。

3. `Retry-After=5s`、jitter=`250ms` 时，为何不能只等待 5 秒？

`Retry-After` 存在时至少等待该时长；缺失或无效时指数退避加 jitter，失败请求本身也消耗每分钟限额，不能紧密循环

4. `call_id` 为什么不能充当扣款操作的幂等键？

`call_id` 由模型供应商为工具调用生成扣款操作必须使用业务 `operationKey`、授权与持久化幂等保护

5. 缓存失败结果或允许同 key 不同请求会造成什么故障？

失败缓存会固化临时失败，同 key 不同请求会错误复用旧结果或混淆业务操作

## 新增测试证明与证明边界


1. strict schema 被保留

   1. 正确：SDK 4.52.0 fixture 中 `strict=true`、object、properties、required、`additionalProperties=false` 的本地映射 

   2. 不正确：真实模型一定遵循 schema、所有模型/端点都支持该 schema

2. call_id 往返不变

   1. 正确：当前单调用链路没有改写关联标识

   2. 不正确：供应商会返回有效 call_id、多调用或 reasoning 上下文得到完整支持

3. Retry-After + jitte

   1. 正确：纯函数在固定输入下返回 `5.25s`，且既有测试覆盖总预算停止

   2. 不正确：真实服务器是否发送该 header、实际调度延迟和端到端延迟

4. 永久错误不重试

   1. 正确：provider-neutral 分类为认证错误后不会计算 jitter 或继续重试

   2. 不正确：adapter 对每种真实供应商错误都分类正确、账户/计费状态永久错误不重试

5. 同 key 同指纹

   1. 正确：单进程串行重放命中首次成功结果，handler 可再次进入但底层副作用一次

   2. 不正确：并发竞争、进程崩溃、跨进程一致性、数据库持久性或 exactly-once

6. 同 key 不同指纹

   1. 正确：本地执行器在第二次副作用前明确拒绝冲突

   2. 不正确：分布式节点同时首次写入时不会发生竞争

7. 失败不缓存

   1. 正确：抛异常后相同操作可再次执行并成功

   2. 不正确：异常发生在外部提交之后时不会重复副作用 

8. 多调用拒绝

   1. 正确：当前单调用 mapper fail-fast，不静默取第一个

   2. 不正确：并行调用、依赖排序或批量 tool outputs

## 总结

1. Responses 的 `output` 为什么不能按固定数组下标读取？

`output` 是异构、有序但长度和内容不固定的数组，可能包含：

* `message`

* `reasoning`

* `function_call`

* 其他工具相关 item

模型也可能先输出 reasoning，再输出 function call，因此不能假定 `output[0]` 一定是文本或工具调用。应遍历并按 item 类型分派；只取文本时优先使用 SDK 提供的 `outputText()` 等辅助方法。[Responses API reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

1. strict function schema 的两个关键要求是什么？

对于 object：

* `additionalProperties: false`

* `properties` 中声明的所有字段都必须出现在 `required` 中；可选值通常通过允许 `null` 表达

`strict: true` 只能约束模型生成的参数形状，不能替代：

* ToolRegistry 的运行时参数校验

* 工具白名单

* 身份认证和资源授权

* 业务审批、额度限制、状态检查

* 防止越权和副作用的安全策略

即：Schema adherence ≠ authorization ≠ business validation。[OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling)

1. `call_id` 与 `operationKey`

   1. `call_id` 模型/供应商协议;关联一次 `function_call` 与对应的 `function_call_output`;丢失或错配会让模型无法确认哪个调用得到了结果；不能防止业务副作用重

   2. `operationKey` 应用或业务层;标识一次逻辑业务操作，跨 SDK 重试、应用重试和消息重放保持稳定;每次重试都重新生成会导致重复执行,同 key 用于不同请求会造成错误复用;同一个 `operationKey` 携带不同请求指纹时必须拒绝，不能返回旧结果，也不能覆盖原记录。

1. Function Calling 的五步循环

   1. 应用把用户输入和工具定义发给模型。

   2. 模型返回一个或多个工具调用。

   3. 应用校验参数、检查授权并执行工具。

   4. 应用携带原始 `call_id` 提交 `function_call_output`。

   5. 模型返回最终答案，或者产生更多工具调用。

收到最终答案且没有新工具调用时停止。以下情况也应受控停止：

   * `refusal`、`incomplete`、`failed` 或协议错误

   * 未知工具或参数非法

   * 工具执行失败

   * 达到 `maxSteps`、时间或费用预算

[OpenAI Function Calling—How it works](https://developers.openai.com/api/docs/guides/function-calling)

1. 最后一个允许步骤收到 ToolCall 时为什么不能继续？

因为工具执行只产生 Observation，还需要下一次模型调用解释结果并生成最终答案。

如果已经没有剩余模型步骤，继续执行工具会产生副作用，却没有机会让模型消费结果。因此 Runtime 应在执行工具前检查是否还有足够步骤；不足时返回 `MAX_STEPS_REACHED`，而不是执行一个“无人接收”的工具调用。

1. 如何区分两类 429？

不能只看 HTTP 429，必须检查响应中的稳定错误字段，例如 `error.code`、`error.type`：

   * 临时限流：如 `rate_limit_error`、`slow_down`，通常可以按 `Retry-After` 有界重试。

   * 额度/账单耗尽：如 `insufficient_quota`、`credit_balance_exhausted`、组织或项目 spend/usage limit exceeded，不应自动重试，需要充值或调整额度。

同一个 HTTP 状态码可能要求完全不同的处置。[OpenAI Error Codes](https://developers.openai.com/api/docs/guides/error-codes)

1. Retry-After、指数退避、jitter 和总预算的关系

可以表示为：

```plain
exponential = min(maxBackoff, baseDelay × 2^(attempt-1))
calculated  = min(maxBackoff, exponential + jitter)

有 Retry-After：
delay = max(calculated, Retry-After + jitter)

无 Retry-After：
delay = calculated
```
然后依次判断：
   1. 错误是否可重试。

   2. 尝试次数是否耗尽。

   3. `当前累计等待 + delay` 是否超过总等待预算。

   4. 未超过才返回“等待后重试”，否则停止。

`Retry-After` 是服务器给出的最低等待时间，不能为了满足本地退避上限而提前请求；若它超过剩余总预算，应停止或延后处理。[OpenAI Rate Limits](https://developers.openai.com/api/docs/guides/rate-limits)

1. 两层各重试 3 次会产生多少请求？

如果“重试 3 次”表示“首次请求失败后再试 3 次”：

```plain
SDK：1 次初始请求 + 3 次重试 = 4 次
应用：1 次初始调用 + 3 次重试 = 4 次
最坏：4 × 4 = 16 次底层请求
```
如果“3 次”指总尝试次数，则是 `3 × 3 = 9`。
避免放大的方法是只保留一个重试决策层：应用管理重试时关闭 SDK 自动重试，或者把 SDK 内部尝试次数和等待时间纳入同一个全局预算，并为副作用操作提供幂等保护。

1. 为什么失败不能永久进入幂等缓存？

临时超时、限流或服务过载如果被永久缓存，后续即使服务恢复，同一业务操作也只能得到旧失败，形成“失败毒化”。

当前合理约定通常是：

   * 成功结果缓存。

   * 执行前失败不缓存，允许再次尝试。

   * 同 key、同指纹复用首次成功结果。

   * 同 key、不同指纹立即拒绝，且 handler 执行次数为 0。

但要注意：如果外部副作用已经提交，应用却在写入缓存前崩溃，仍可能重复执行。线上需要持久化幂等记录、数据库唯一约束或供应商幂等支持。

1. 当前离线契约测试能证明什么？

能够证明本地代码的不变量，例如：

   * strict schema 映射保留 `required`、`additionalProperties:false` 和 `strict:true`。

   * `call_id` 在 SDK → core → ToolResult → SDK 往返中保持不变。

   * Registry 在 handler 执行前拒绝 missing、extra、blank 和未知工具。

   * RetryPolicy 正确处理 Retry-After、jitter、永久错误和等待预算。

   * 同 operationKey、同指纹只执行一次；不同指纹被拒绝。

   * Runtime 能执行 `maxSteps` 和 typed failure 等停止策略。

它不能证明至少以下线上性质：

   * 真实供应商可用性及模型实际遵守 schema 的程度。

   * 实际网络、代理、TLS、超时和端到端延迟。

   * 真实限流响应、`Retry-After` 行为和 SDK 自动重试整合。

   * 账号权限、额度、计费和线上配额。

   * 多线程或分布式幂等一致性、进程崩溃恢复。

   * 真正的 exactly-once 副作用语义。

   * 多工具并行调用及 reasoning items 的完整续接。

   * 供应商升级或 SDK 版本变化后的兼容性。
